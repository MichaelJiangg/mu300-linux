# VoLTE / VoNR 状态显示为空修复（2026-10-20）

## 已确认的问题

连接的 F50（内核 7.2.8）通过现有 AT 适配器返回：

- `AT+CAVIMS?` → `+CAVIMS:1`、`OK`。
- `AT+SP5GCMDS="get nr synch_param",42` → `+SP5GCMDS: get nr synch_param,42,1`、`OK`。

但是网页锁定状态缓存的 `volte.enabled`、`vonr.enabled` 都为 `null`。

应用网络设置后，工作进程尚未释放 `APPLY_DIR` 就执行 `get fresh`。
旧的 `voice_json` 在此时跳过实际查询，只读取本次启动内的写入凭据。
未曾操作过的语音开关没有凭据，因此被写成未知并缓存十分钟。
只设置其中一个语音开关时，另一个也会出现同样问题。
这是状态显示缺陷，不能据此认定 IMS 注册或语音业务异常。

## 修改

实际刷新通过原有 AT 适配器读取两个状态，包括应用完成后由持锁工作进程直接启动的刷新。
通过锁文件 PID 与刷新进程的父 PID 判断归属；其他进程仍不在应用过程中插入语音查询。
查询不修改或创建写入凭据；真实查询失败仍返回未知，不用保存配置冒充实际状态。
写设置的互斥锁、SIM 寻址、射频切换和开机回放保持原有实现。

- `test_lock_jobs.py` 完整 55 项测试通过；最终版本的 3 项针对性回归也均通过，覆盖 dash 与 BusyBox ash。
- 新增回归：应用 EN-DC 后两个未操作的语音状态仍可读；单独修改 VoLTE 后 VoNR 状态仍可读；无关读取进程在应用期间不发送语音查询。
- F50 上以只读方式模拟持锁刷新：旧文件返回两个 `null`，新文件返回两个 `true`。
- 已热部署公共 `lock-apply.sh`，经网页实际使用的 HTTP JSON-RPC `mu300dash.lock_get` 确认两个状态均为已开启。
