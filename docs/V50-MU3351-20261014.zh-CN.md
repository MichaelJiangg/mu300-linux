# V50 / MU3351 适配记录

## 实机与 F50 对比

2026-10-14 对已连接 V50 做只读检查。产品名 `V50`、设备名 `MU3351`、
SoC T760、平台 `ums9620`、板名 `ums9620_2h10_feimao`，和 F50 属同一内核平台。
三簇 CPU 的频率候选与已有 F50 原厂表一致；无线侧也是 PCIe SC2355，
WCN、WLAN、蓝牙驱动属于同一家族。A/B 分区命名相同。
ZTE [官方支持页](https://www.ztedevices.com/cn/supports/v50/)将 V50 标为 MU3351，
不能和 Blade V50 手机混淆。

- 灯由 I2C3 地址 `0x5b` 的 AW9523B 驱动，F50 的参考 DT 不含此控制器。
  V50 同时暴露 `aw_led/red/green/blue` 和 `sc27xx:*`，旧脚本优先选择 PMIC，
  因此并不是仅把名字加进白名单即可完成灯光适配。
- 这台 Android 13 的 userdata 是 FBE（`encrypted` / `file`）。
  GPT 空闲区域足够时无需缩容或重置；只有必须从 userdata 腾出空间时，
  才走清空 userdata、Android 初始化、重新授权 root、续装流程。
  这是本机当前状态，不能据此推断所有 V50 或 F50 的加密方式。
- 本轮未检测到插入的 TF 卡，不能因此断言机器没有 TF 卡槽。
- 厂商固件和 Android 运行库仍从安装目标本机提取，不能替换成 F50 的文件。

最初探测阶段仅只读。后续已部署 V50 内核和公共脚本、离线修复 OpenWrt ext4，
写入 Linux B 槽及 misc 的 32 字节启动控制；没有格式化 Android userdata、
更改 GPT、写 Android A 槽或 NV。相同平台不代表所有功能均已实物验证。

## 实现

桌面安装器只接受精确的 `V50` + `MU3351` + `ums9620` 组合；
公共启动链检查与切换模块同步支持，两份 bootchain 脚本保持一致。
initramfs 和运行时依据实际 AW9523B 节点识别为 `v50`，沿用 F50 的核心模块和
`192.168.77.1` LAN 地址。运行时更新允许使用共同内核平台的包。

补入 `CONFIG_LEDS_AW9523B=y` 和 LED 专用驱动，兼容原厂 DT：
仅绑定 `awinic,aw9523b`、`led_enable=1`、`gpio_enable=0`；
验证引脚组、亮度上限和芯片 ID 后初始化。亮度变更使用同步 I2C 写入，
不增加轮询、IRQ 或常驻动画线程，卸载与关机熄灭通道。
这是 6.18/7.2 的新源码，不是把 Android 5.4 ko 强行加载到新内核。

已逆向 Android `aw9523b_brightness_work`（`0x3424`）确认：
`idx` 是 GPIO 引脚编号，并非 DIM 寄存器直接下标。
P0_0–7 对应 `0x24–0x2b`；P1_0–3 对应 `0x20–0x23`；P1_4–7 对应 `0x2c–0x2f`。
`aw9523b_set_led_imax`（`0x35ec`）只使用 DT `default_imax` 的低两位。
保留原厂绿组上限 80、红/蓝/全灯组上限 120。

已进一步逆向原厂 `groupcolor_store`，并结合用户的单组点灯确认修正映射。
原厂 `green` 组实际是白光，不能用 RGB 混色代替；有独立 NET1、NET2、Wi-Fi 灯：

| 灯 | 白色引脚 | 蓝色引脚 | 红色引脚 |
| --- | --- | --- | --- |
| NET1 | 8、11 | 9、12 | 10、13 |
| NET2 | 14、1 | 15、2 | 0、3 |
| Wi-Fi | 4、5 | 6 | 7 |

驱动保留原厂组接口，另提供 `v50:net1:*`、`v50:net2:*`、`v50:wifi:*`
和 16 个原始 pin 类。只有原厂完整掩码匹配才暴露物理组，不盲目套到其他 AW 板。
LuCI 三组独立开关和亮度，包含中/英/土语言。亮度按白光 80、蓝/红 120 限幅。
旧兼容接口在 V50 上不争用 AW，也不误驱动 PMIC。

OpenWrt 把 NET1/NET2 适配为 SIM1/SIM2 注册状态，LTE 蓝、NR 白、无卡熄灭、
离线红；这与原厂按运营商/内置或外置卡定义 NET 灯的策略不同。
Wi-Fi 5 GHz 白、2.4 GHz 蓝。注册变化从现有持久 AT URC 读者传递，
Wi-Fi 使用 ubus 事件，闪烁使用内核 LED timer，不增加常驻 AT 轮询或用户态闪烁线程。

避免源命令失败被编码器掩盖。覆盖 GPT、misc、boot 的读取和备份。

`cb078f2cea210bca36a2976dca99eb59c86afdc39ee116f59d608a81b9839870`。

## 双卡、CPU 与其他功能

- 一次性 V50 平台默认值补入 `sim_slots=2`，保留用户选择的上网卡。
  NR3 作为第二张卡的 URC 读者，所有 AT 通道所有权在干净启动时配置。
- 双栈启动先读 CPIN。只对已插卡的协议栈执行 SFUN 与模式初始化，
  避免仅 SIM2 插卡时给空 SIM1 上电触发 CP 断言。实机确认 SIM1 未插，
  SIM2 CPIN READY、CFUN=1、双栈就绪标记存在。注册曾返回 CEREG=8，
  不将此描述为成功普通上网；双卡同时插入的网络仍需实物验证。
- V50 原厂 SML 与已支持的 F50 仅认证尾部有差异，DVFS 代码/表逐字节一致。
  电压白名单按完整的实际 SML 哈希加入 V50，不放宽未知固件。实机读取支持，
  三簇频率/调速器及可写温控接口可用，没有给用户预设降压或改写 SML。
- USB 角色 setter 同步沿用 F50 路径，修正被 U30Air 专属入口拒绝的情况。
  本轮未做 V50 OTG 外设实测。
- NFC 已确认 I2C2、地址 `0x57`、AP GPIO189，读到 NFC Forum 能力容器，
  NDEF 容量 872 字节；U30Air 使用 GPIO190，不能照搬引脚。
  适配器从本机 DT 读取复位 GPIO，并仅接受已验证的 V50 绑定。
  热点信息同步、RF 开关与现有文本/URL 功能共用已有 FM11 标签实现。
  实机 status/sync 读写复验通过，保留用户自定义文本/URL 不自动改成 Wi-Fi。
  OpenWrt 的 `config.change/wireless` 事件已注册，更新热点配置时同步标签，
  不增加定时轮询。修正静态 BusyBox 工具路径、短延时及 awk 字符串拼接兼容性。
  NFC 8 项测试含真实 BusyBox shell，均通过。

## EXT4 元数据损坏与 eMMC 恢复

本节记录早期 V50 `#17` 对照。后续公共策略、FUA 兼容及根因确认边界见
[两仓库报告](DUAL-SIM-BOOT-EMMC-20261014.zh-CN.md)，不能用旧策略的观察
冒充新完整策略已完成实机验收。

原运行时出现 `ext4_lookup: deleted inode referenced`，含义是目录里的文件名
仍引用某个 inode，但 inode 已处于删除/无效状态。配置和原子替换后的脚本
曾在正常重启后丢失；离线 fsck 修过一次后再次重启仍复发。
因此既不是单纯容量显示错误，也不能把 fsck 当作根因修复。

主要线索是 V50 eMMC runtime PM：运行中宿主自动休眠，实验在 initramfs
写 `power/control=on` 触发的恢复停在挂载/fsck 之前。针对该板的非可移除
eMMC 宿主，在驱动 probe、第一次 autosuspend 之前执行 `pm_runtime_forbid`。
保留 HS400 ES、200 MHz、ADMA 和软件队列；可移除 TF 及其他板不套此策略。
错误分支和移除路径配对释放 PM 引用，不用常驻进程反复唤醒。

在 Android 下离线修复 `mu300root`，恢复配置和脚本、卸载后只读 fsck 校验。
新内核 `7.2.8 #17` 实机显示 `control=on`、`runtime_status=active`。
随后 Linux 写入测试标记、提交配置、同步并正常重启，标记/配置/关键脚本 SHA256
全部保留，EXT4 `errors_count=0`。这是改善的实机证据，但目前还不足以证明
所有旧元数据损坏都由 runtime PM 单独造成，需要继续观察跨重启持久化。

桌面 initramfs 另增加异常 ext4 的离线自动检查：正常 clean 超级块不跑完整
fsck；出现错误标志或明确修复请求才执行 e2fsck，并在检查期间开放 USB 恢复。
不会在挂载中的根分区直接修复，也不会把此前失败的用户态 PM 恢复实验带入最终启动。

## GPT 空闲空间安装

2026-10-14 实机只读确认物理 eMMC 122159104 个 512 字节扇区，约 58.25 GiB。
当前 userdata 为 p75，OpenWrt p76 为 8 GiB；p76 之后仍有约 32.39 GiB
GPT 未分配空间。这证明新安装优先缩 userdata 会造成不必要的 Android 重置。

新桌面路径先校验 GPT 两份副本、usable bounds、分区重叠、空表项，
优先使用足够大的连续空闲区。只在不够时才进入旧缩容逻辑。
FBE/FDE 不阻止空闲区安装；本机固件仍由当前已解锁 Android 提取。
使用原生 Android 有 size limit 的 loop，写入/扩容/只读校验后才提交新 GPT，
最后校验 boot 和切槽。不会要求 Android 重读正在使用的整盘分区表。
旧原始偏移系统签名会排除其所在空闲区域，不静默覆盖已检测的旧系统。

离线 GPT/FBE 路由和失败阻断测试通过；Linux 稀疏虚拟磁盘完成真实 ext4
写入、扩容至 2 GiB、e2fsck、文件校验、GPT 提交，前后保护区未变化。
本机已有独立 OpenWrt，因此仅探测，没有在实机新增分区或再缩 userdata。

## 实机续装：loop 路径修复

用户完成 FBE 缩容与 Android 重置后，续装报 `losetup: ...openwrt.ext4.new: No such file or directory`。
只读检查确认镜像仍存在、大小为 2 GiB。BusyBox `losetup -f` 返回 `/dev/loop31`，
实际 Android 节点是 `/dev/block/loop31`，报错并不表示镜像丢失。
新增 Android loop 解析助手，优先选择真实 block 节点；若 ueventd 尚未创建节点，
按 sysfs 的 major/minor 在私人暂存目录创建，保持对普通 Linux 节点的兼容。
镜像首次/只读挂载失败时也会卸载自己已绑定的 loop，不遗留占用。

第一阶段尾部的空错误发生在 shell 重启断开 ADB 时。改用 ADB reboot 服务，
并给没有 stderr/stdout 的 ADB 失败补充动作与退出状态，不再输出空错误。
Wi-Fi 密码按用户要求改为明文输入，SSH 密码仍使用隐藏输入。

修补用户当前解压目录的 EXE、Python 和镜像脚本，备份旧文件及原续装记录。
修补前完整核验旧包及记录绑定；修改后重新核验所有原 Magisk 文件和 boot/工具资产，
更新该条记录的包绑定，保留设备、槽位、分区几何与令牌，没有放宽通用续装校验。

实机验证：解析到 `/dev/block/loop31`，只读挂载/卸载成功；在原失败的临时镜像内
完成系统解包、提取本机运行库/固件、文件哈希和只读复验，返回 `IMAGE-INSTALLED partition-write`。
现有独立分区 8 GiB，续装身份、几何、令牌和包绑定均通过。
本次修复没有重新缩容、格式化 userdata、写独立分区或切换启动槽。
最终写入与 OpenWrt 首次启动仍由用户继续菜单 5 完成。

后续已将整包清单绑定改为关键载荷身份校验，允许修补版安装器和目录搬迁，
设备、槽位、8 GiB 分区几何及准备令牌检查保留。旧记录的确切原清单已恢复到
电脑备份目录，`clean-layout` 新版 EXE 的只读续装预检通过。

## F50 / V50 共用固件的机型隔离

2026-10-14 补齐代码，尚未重新编译、打包或部署本节改动。

- 旧 `install.sh` 与桌面安装器对齐：V50 必须同时匹配 `V50`、`MU3351` 和
  `ums9620`，身份不一致时拒绝安装，不再确认后误标为 F50。ADB 设备选择支持 V50，
  仍在存在多台设备时要求选择；不会把 `V500`、`MU33510` 当作匹配项。
- initramfs 和 `mu300-device` 优先采用本机设备树，旧镜像里的 `f50` 标记不能遮盖
  V50 的 AW9523B 控制器。F50 也不会因为残留 `v50` 标记被识别成 V50。
  只有没有设备树的兼容环境才读取已有标记，并限制为三个支持的机型。
- `mu300-platform-config` 为 F50、V50、U30 Air 记录配置所属机型。
  检测到其他机型的配置备份时，启动 AT 服务前重设卡槽数、默认数据卡、
  自定义切卡适配器和 SIM 网卡映射；F50/U30 Air 默认单卡，V50 默认双卡。
  同机型后续启动不覆盖用户设置；APN、短信、流量账本和网络配置不在清理范围。
  没有历史机型标记的旧 F50/U30 Air 配置只补标记，保留既有手动适配，
  因此无法追溯识别完全不含来源信息的旧备份。
