# TF 容量预检误报排查（2026-10-16）

用户日志的目标是 F50 的 `/dev/block/mmcblk1p1`：61,067,008 个扇区，
31,266,308,096 字节，约 29.119 GiB，符合标称 32 GB 卡的可见容量。
失败位于 TF worker 的 `preflight`；没有进入释放挂载、格式化、根系统写入、
boot 写入及 misc 设置阶段。电脑备份已完成。

原错误 `TF capacity too small / invalid requirements` 同时表示容量不足或需求
文件非法，不能据此认定卡太小。日志没有记录需求文件内容，因此仍不能仅凭日志
确认现场的两项需求数值。传输文件长度为 14 字节；当前同版本需求示例
`351656 18357` 加 LF 为 13 字节，加 CRLF 为 14 字节，故换行问题与现场相符。

已在真实 BusyBox ash 中复现：原先直接 `read` 会将 CRLF 的 CR 留在 inode
数字尾部，随后被数字检查拒绝，出现相同的容量/需求文件误报。
`tf-payload-manifest.py` 原来未指定需求文件换行，Windows 会生成 CRLF。

修复如下：

- 需求文件生成固定为 ASCII、LF，哈希按实际生成字节计算。
- 共用 TF 存储脚本统一读取需求，接受 LF/CRLF 与无末尾换行，拒绝坏数字、
  多余字段、重复记录和零值。不修改已有需求文件，保留其原始载荷校验。
- TF worker 与 Android TF 格式化/安装入口都复用该读取函数，适用于 GUI、CLI
  和 Magisk 的共用 TF 路径。
- 错误区分需求格式非法和容量不足；容量日志记录目标扇区数、需求 KiB、inode，
  真正不足时同时报告目标与需求 KiB。不增加容量上限、不重分区、不绕过校验。

验证结果：

- Windows：新需求文件生成测试通过，检查输出没有 CR，且载荷哈希一致。
- WSL/Linux：新增 6 项需求/预检测试、现有 TF 可靠性 14 项及格式策略 1 项均通过。
- 使用日志中的 61,067,008 扇区验证 LF/CRLF，通过；128/256 GiB 纯数值测试通过。
- 实际 BusyBox worker 预检使用临时普通文件与受控 I/O 函数：有效需求通过，
  坏需求和实际容量不足被准确区分；模拟卡、boot、misc 文件保持零字节。
- `git diff --check` 通过。
