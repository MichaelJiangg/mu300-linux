# 长短信分段接收修复

## 已确认的问题

`mu300-sms import-pdu` 原来只把 UDH 的参考号、总段数和序号写入记录，
没有重组，每个分段直接成为一条可见短信并可能单独被转发。
多个长短信交错到达时，页面按入库 ID 展示，表现为拆散、乱序。
旧文本同步还有按“发送人 + SCTS”拼接的逻辑，既不能知道真正段序号，
也可能把同一秒的独立短信误合并。

## 新行为

- 使用发送人、参考号及其 8/16 位类型、总段数、编码、PID、语言表和 SMSC 分组。
- 以网络 SCTS 的 10 分钟距离检查参考号复用；不是按本机到达时间超时丢弃。
- 分段先原子保存到本卡短信池的 `multipart/`，保留原始 PDU，成功持久化才允许 ACK。
- 不完整的分组不进入 `msg/`、不分配可见消息 ID，因此不会提前触发转发。
- 收齐后严格按 1..N 拼接，只发布一条完整短信，然后清理已合并分段。
- 保存各段原始 PDU 指纹，重复投递不重复发布；删除后重投也不会复活。
- 进程退出或重启后从持久化分段继续；SIM 归档和直接收信共用同一重组入口。
- 混合 SIM 历史导入的组保持 `source: sim`，避免完成重组时变成实时短信转发。
- 遇到多个无法区分的候选组，不猜测串接、不覆盖已保存段；保留原始输入并报告失败。
- 文本模式缺少 UDH，不再按发送人/时间强行猜合并。正常收信优先走 PDU 路径。

无新运行时依赖，无 AT 轮询，无新增等待。修改的是 rootfs 原有脚本和 AWK，
各种安装方式复制同一套文件，无需插件前端另作拼接。

## 验证与边界

`python tests/test_sms_multipart.py` 使用真实 shell 和 PDU 解码/入库代码，
测试倒序、三条交错、重复、参考号位宽隔离、跨分钟、跨日期复用、缺段、
历史来源、删除后重投、冲突保护、重启续收和单段兼容。
测试使用隔离目录，不访问 AT、不修改实机短信、不发送邮件。

本次未做运营商实机长短信接收测试，未热部署。
修改不自动重写此前已拆散的可见短信：旧记录未保留完整 UDH/原始 PDU，
不足以安全判断哪些段属于同一消息；不能依靠发送人和时间盲目“修复”历史。
