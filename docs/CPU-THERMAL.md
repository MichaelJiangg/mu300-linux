# CPU 温控管理

CPU 设置页的温控功能使用标准 thermal sysfs，不调用 AT，不依赖 MU300 温区编号。
与 E5 对齐到单个温区、单个 passive trip 的粒度：温度实时显示、逐项阈值、
实际 CPU cooling 绑定和降温等级、开机持久化、恢复启动基线。
critical/hot 阈值和 hysteresis 只读，不提供关闭保护或任意 sysfs 写入。
页面固定按“频率 → 电压 → 温控”排列。三块独立提交和恢复，保存一块不会提交、
覆盖或校验另一块尚未保存的编辑；频率与温控各自有开机自动应用开关。

## F50 主线内核

原厂 DT 的 19 个物理传感器没有独立 trips。`virtual-sensor@0` 的 `thmzone-cells`
引用 11 个物理温区，原厂 `soc-thmzone` 上才有 70°C 被动监测、85°C CPU 降频、
110°C 临界保护。过去 6/7 主线缺失 `virtual-thermal` 驱动，虽然有 cpufreq
cooling devices，却没有原厂虚拟温区将二者连接。

`upstream/modules/mu300_thermal` 恢复该虚拟传感器：取 DT 引用温区的最高温度，
复用原厂 trips、polling 和 cooling maps；物理传感器未就绪则 deferred probe。
任一读取失败返回错误，不把失败解释为低温。两套受支持内核的物理传感器均内置。
模块由真实 rootfs 的 `extra-modules` 加载，不在 initramfs 启动，也不增加常驻工作线程。
5.4 保留自身实现。

`thermal-guard` 只有在原厂温区启用、所有现有 CPU cooling devices 都已绑定后，
才让内核接管频率限制，避免两套控制器争用。缺少绑定时仍使用旧兜底。
主线仍保留原来的 105°C 紧急关机保护及温度 LED 提示；插件不能改该保护。

## 配置与保护

- 可写项必须是具有 CPU cooling 绑定的温区内、内核允许写入的 passive trip。
- 调整范围 40–100°C，且不高于最低 hot/critical trip 减 10°C；步进 1°C。
- 同温区 passive trips 必须递增且至少间隔 1°C；所有输入先验证再写入。
- 降低阈值时先改低位，提高阈值时先改高位；写后回读，失败逆序回滚。
- 通过现有 CPU 写锁串行化；页面隐藏时不轮询，实时刷新不覆盖正在编辑的值。
- 只改温控时不重写未修改的频率项；已保存的频率请求不会被临时温控限频覆盖。
  已接受的频率上限写入若被实际 CPU cooling device 限制，不误判为写入失败。
- `/etc/unisoc-modem/cpu.json` 使用 v2 的独立 `frequency` / `thermal` 配置段。
  写锁内原子更新所选段，保留另一段。取消自动应用、恢复基线均只清除所选段；
  两段都清除时才删除文件。温控按名称而非易变编号匹配。
  v1 纯频率和旧合并配置均兼容；读取和启动回放不修改旧文件，首次保存时迁移。
  拒绝旧页面提交的混合请求，提示刷新，防止一次点击误改两块。
  名称重复、温区缺失或只读时拒绝，不盲目写入。
- S99 捕获 `/run/unisoc-cpu-defaults.json` 后回放配置；晚出现的温区在首次修改前补录。
  两个配置段独立回放，一项能力缺失或验证失败不阻断另一项。
  “恢复启动基线”仅恢复对应区域的本次启动记录值并取消该项开机应用。热安装首次捕获的是
  当时实际值，不宣称是任意固件的出厂默认。
- 电压继续独立保存、重启生效，未改变电压恢复保护。
