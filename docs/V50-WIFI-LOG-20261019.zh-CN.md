# V50 Wi-Fi 不稳定反馈：2026-10-19 日志复核

## 范围和结论

只读分析用户提供的 `v50-op_2026-10-19` 文件夹及本仓库驱动代码。
没有操作实机、改配置、编译、打包或开启采集。

**确认存在 PCIe 发送队列反压，以及初始化 RF 配置的非零固件应答。
深入原厂对照和实际函数执行后，另确认 RX 补充存在“总线已恢复却仍等退避”
的时序缺口；它是需要处理的具体恢复迟滞，但尚不能认定本机每次不稳定
均由它造成。日志没有复现运行期间客户端反复离线、热点消失或 WCN assert。**

这与 T512N 的 Marlin3Lite 拼接固件选择问题不是同一条已确认故障路径。
V50 此处使用 PCIe、`sc2355_marlin3` 固件，不能直接套用 T512N 的结论。

## 确认的现象

### 1. PCIe 通道 10 暂满，但不能换算成丢包

内核日志有 45 条限频后的 `edma_pending_q_buffer(10) full`，累计
`rejected submissions` 从 1 增至 312；可见 280 条 `push link fail`，
返回码全部为 `-11/-EAGAIN`，另有日志抑制提示。

首次出现在 uptime 99.291 秒，后续呈突发分布，例如 300–330 秒可见 47 条。
最后一次在 603.998 秒，不能声称整个问题已经恢复。

`upstream/modules/wcn_bsp/pcie/edma_engine.c` 的 pending ring 满时拒收
本次链表；`sc2355/tx.c` 对 `-EAGAIN` 保留业务队列，不增加连续硬错误预算，
`sc2355/pcie.c` 通过 DMA 完成回调唤醒重试。此日志至少符合新的总线返回码，
但没有加载模块 Build ID，不能由此证明全部配套补丁的加载状态。

312 是拒绝提交尝试的累计数，不是 312 个独立业务包，也不是 312 次断网。
现有记录没有逐包等待时间、业务吞吐和客户端重传率，不能量化用户影响。

### 2. RF 配置第三段收到 UNKNOWN_ERROR，不能忽略但也不能直接定罪

两次 WLAN 初始化均出现：

1. 读取 `wifi_board_config.ini`，长度 `0x1dc4`（7,620 字节），解析返回 0。
2. 第一、第二段配置下发后，开始第三段 RF 配置，`rf_data_len=141`。
3. 紧接着收到 `CMD_DOWNLOAD_INI / SPRD_CMD_STATUS_UNKNOWN_ERROR`。
4. 驱动继续下发第四段并启动热点。

对应时间为 uptime 21.216709 和 45.811423 秒，第二次上下文位于内核日志
3316–3328 行。`cmdevt_handle_rsp_status_err()` 只将该命令的 CRC、索引和长度
错误转换为失败；UNKNOWN_ERROR 仍可让调用者继续。因此“解析成功”和“热点
启动”均不能证明固件完整接受了这段 RF 配置。

此现象在历史 F50 日志中也出现过，并不专属于本 V50，更不是本次刚引入的
已确认回归。需要同一 V50 固件版本的 Android WLAN 模块/初始化日志，核对
第三段格式、所选 INI、返回状态及后续处理；不能把换另一机型 INI 当作修复。

另有 `CMD_POWER_SAVE / ARG_ERROR` 和若干 API version 差异。版本差异本身
不等于不兼容：驱动有 API 协商，ID 11 是扫描接口，不能把所有差异都归因于
热点数据路径。省电命令的具体子类型/参数没有出现在日志中，不能据此禁用休眠。

### 3. 每 6 秒一次 change_beacon，不足以证明信标抖动

共 93 次 `sprd_cfg80211_change_beacon`，相邻调用的中位间隔为 5.999316 秒。
这与周期性 BSS load 更新相容，但没有 hostapd 配置，不能确认具体触发源。

`common/cfg80211.c` 在入口直接打印该消息；随后只按非空附加 IE 调用
`cfg80211_set_beacon_ies()`。该打印不能证明完整信标模板已被重写，更不能证明
空口信标漏发。280 条可见暂满日志中，仅 2 条距最近更新调用不超过 0.1 秒，
没有“每次更新后立即失败”的简单时间对应。

这份日志不支持直接认定 `bss_load_update_period=60` 与
`disassoc_low_ack=1` 叠加导致掉线，也不支持据此全局屏蔽用户配置。

### 4. SIPA、MMC 告警需分开解释

- 11 条 `sipa overflow on ep:1 evt=0x10000`，均伴随 `node transfer err=2`；
  其中 9 条在 uptime 31.5–48.5 秒，另两条在 428.075 和 429.577 秒。
  `0x10000` 是发送完成错误事件，真正 FIFO overflow 位为 `0x20000`。
  原厂描述符错误码 2 的准确语义仍未知，不能凭名称判断蜂窝 FIFO 满或强行重发。
- 92 次无在途命令的 MMC command interrupt，其中 mmc2 91 次、mmc1 1 次。
  本日志已明确 mmc0=`22200000.sdio` 且承载 eMMC，mmc2=`22220000.sdio`；
  Wi-Fi 则走 PCIe。这不是 eMMC 发生 92 次写超时。
  `Timeout: 0x00000000` 是寄存器转储值，不是超时事件。
- ext4 启动时 journal recovery complete，随后正常读写挂载；没有当前日志中的
  ext4 元数据错误、eMMC I/O 错误或 OOM/panic 证据。

### 5. 连接记录不支持“反复被踢”

uptime 45.935 秒的 `del_station reason:2` 出现在热点初始化阶段，
早于 52.461 秒唯一的 `New station connected`，且脱敏 MAC 标识不同。
不能把这一条当作后续已连接手机的异常断线。

52.889 秒有两条实际 `TX Err` 丢弃日志，紧邻首次接入后的 DHCP REQUEST/NACK；
没有返回码或包头，不能追溯两条被丢弃报文类型。后续没有相同日志，也没有
运行期间的断开事件、CMD_TX_DATA 非零应答、WCN assert 或固件重启证据。
系统日志仅保留少量用户态消息，没有完整 hostapd 事件流，所以不能反推用户
没有遇到卡顿，或用“没看到断开”证明网络稳定。

## 深入对照后的结果

### 原厂固件和 INI：未发现原先怀疑的明显选择/解析错误

只读提取本地 `V50_B15_Oem_Lock_20250726174705.7z` 的 super 中的
`odm_a`、`vendor_dlkm_a`，在内存盘只读挂载其 EROFS 镜像；没有访问实机。

| 原厂文件 | SHA-256 |
| --- | --- |
| sprd_wlan_combo.ko | `32b19d68491fc67782aed2713e9de379bde62707d8c47ece0b782f1c5e62692c` |
| wifi_board_config.ini | `b3ec024aa4e530930f2a55a77b01c89a2b1eb2225d4456ebaab3d3c529562af2` |
| wcnmodem.bin | `393c25e596c0ed46adc65cd9c9459d8617afc8fdcb47b3e5cf4da35a9b82424e` |

WCN 内嵌版本字符串与群友日志一致，为 `W25.15.2 / sc2355_marlin3 /
04-08-2025 16:38:31`。版本字符串相同不是故障机二进制 SHA-256 相同的证明。

从原厂 WLAN 模块的 `sc2355_nvm_table` 和重定位表读取 152 个字段定义，
按原厂字段偏移和宽度将原厂 INI 重建成配置；原厂
`sc2355_download_hw_param` 的反汇编确认四段偏移和长度。
复算原厂 CRC 算法后，四段全部与群友日志匹配：

| 配置段 | 字节数 | 原厂数据复算 CRC | 群友日志 CRC |
| --- | --- | --- | --- |
| SEC1 | 328 | 55899 | 55899 |
| SEC2 | 1464 | 19724 | 19724 |
| SEC3/RF | 141 | 17542 | 17542 |
| SEC4 | 3 | 18003 | 18003 |

这显著削弱了“用错 INI／解析错结构”的怀疑，但 CRC16 匹配不能证明固件
最终采用了配置，也不能代替故障机固件的完整哈希或原厂运行日志。

原厂 `sc2355_get_nvm_table` 在 XPE eFuse 为 1 时选择
`wifi_board_config.xpe.ini`，否则普通 INI；群友启动日志已经读到 XPE=0，
因此这里选择普通 INI 与原厂分支相符。不是 T512N 那个已证实的固件选择问题。

更正先前对 UNKNOWN_ERROR 的解读：它是 `cmdevt_err2str()` 的 default
字符串，不是一个已知数值错误码的准确名字。当前日志没有打印原始 status，
因此只能确认非零且未被字符串表识别，不能据此宣称“RF 被拒绝，所以网络差”。
原厂和现有驱动的四段下载布局一致，不应盲目跳过第三段或换另一机型 INI。

### 发送 pending 队列容量与原厂相同

原厂模块的 `sc2355_pcie_hif_ops` 包含六个通道记录（每条 144 字节）；
通道 10 的 `pool_size=300`、`max_pending=4`，与现有配置相同。
不能把 4 简单认定为移植时缩小了队列，也不以扩队列作为本次根因修复。

业务 TX 的 `-EAGAIN` 回退仍保留消息及数据缓冲；pending DMA 完成后的唤醒
已存在。未在这份日志发现硬错误预算耗尽/flush 的证据，不重复添加同一修复。

### 找到并复现：RX 补充对 EDMA 恢复缺少即时推进

具体调用链：

1. `pcie_init()` 将 `hif->tx_data_port` 设为 10。
2. 该通道既发送 WLAN 业务数据地址，也发送供固件接收空口报文的 RX 缓冲地址。
3. `sc2355_tx_addr_trans_pcie()` 在暂满时保留待发 RX 地址链表。
4. `sc2355_mm_fill_buffer()` 发现这轮没有进展，使用
   20→40→80→160→320→640→1000 ms 退避安排 RX 重试。
5. 只要 `delayed_work_pending(refill_retry)` 为真，之后的 RX 补充请求直接返回。
6. `sc2355_pcie_tx_data_complete()` 在 DMA 恢复后只处理 `pcie_tx_waiting`
   并唤醒 TX 线程，不取消/提前 RX 的延后任务；TX 线程也不推进这条 RX 地址链表。

因此，EDMA 已有空间并不意味着 RX 地址能立刻补充。这与原厂
`sc2355_mm_fill_buffer` 的立即重新排队存在实质时序差别。

使用从生产源码直接提取的上述两个函数，构造“RX 地址链表已经创建、
暂满后 DMA 立即恢复”的状态，分别覆盖 TX 等待标记为 0/1 及八种退避状态：
16 个离线用例通过 ASan/UBSan 执行，确认总线恢复后连续八次补充请求仍不提交，
只有模拟退避定时器到期才提交成功，复现额外 20–1000 ms 的门控等待。
这不是 wall-clock 性能测试，也没有测量故障机的实际延迟。

现有 `test_wcn_recovery.py` 验证了“定时器未到不能绕过退避”以及“下一轮真正
执行时进展会清除退避”，未覆盖“DMA 已腾空间，应提前恢复 RX”的跨路径场景。

驱动设置了最多 500 个 RX MH 缓冲。若等待期间可供固件使用的 RX 缓冲耗尽，
手机上传及下载依赖的 TCP ACK 等返回报文均可能受影响。这提供了可以解释
短时卡顿的具体机制，**不是本次日志已经记录缓冲耗尽或最长一秒停收的证明**。
312 次暂满也未区分业务地址/RX 补充地址，不能当作 312 次退避触发。

正确处理方向是保留固件异常/分配失败时的防空转退避，在确切 DMA 完成事件
表明总线有进展后，以原有串行工作队列提前推进待补地址；不能从 IRQ 直接并发
执行补充，也不能简单删除全部退避或重新加入常驻轮询。这一轮只分析和复现，
没有修改生产驱动或声称已完成硬件修复。

### 低 ACK 踢人说法也缺少本驱动入口

核对当前 WLAN 源码，仅存在 `cfg80211_cqm_rssi_notify()`，没有
`cfg80211_cqm_pktloss_notify()` 的上报调用；`EVT_CQM` 处理的是 RSSI 与
beacon-loss 的 STA 通知。不能把两条普通数据发送 `TX Err` 直接串成
hostapd 收到 low-ACK 事件后主动踢人。此结论不排除固件自身断开或其他
管理事件，但本日志没有这些证据。

## 后续修复优先级

1. 优先完善已离线复现的 RX 补充恢复时序，保留故障退避并验证完成/退出竞争，
   不增加轮询、不放大队列、不改固件/NV。
2. 若继续判断这台机器的全部不稳定原因，需要区分 Wi-Fi 关联断开和数据卡顿，
   并区分业务/RX 地址提交及实际恢复时刻；现有日志无法回溯这些数据。
3. 保留 RF 非零应答线索，但先补明确数值语义或原厂运行对照，不以未知字符串
   判定硬件参数错误。beacon 入口日志同样不能替代空口信标证据。
