# V50 SIPA 与 Wi-Fi PCIe 错误日志分析（2026-10-18）

## 范围与结论

分析用户提供的 `v50-mu300-openwrt-7.2.8-20261017.log`，以及当前
`clean-tf-7.2` 的 SIPA、WCN PCIe、WLAN 源码。未操作实机，未修改驱动、
配置、NV，也未开启采集。文件名不能证明设备实际加载了哪个提交的模块。

**日志证实 SIPA 发送完成错误与 Wi-Fi PCIe 队列反压同时存在，不能证明
两者的因果关系。这里的 SIPA “overflow” 不等于硬件 FIFO 溢出。**

日志覆盖内核 uptime 2853.838513–2930.907992，约 77 秒，开头已经在报错，
不包含首次触发过程。墙钟为日志中的 2026-10-18 GMT+3 18:17:19–18:18:36。

## 已确认的证据

| 现象 | 日志事实 | 源码含义与边界 |
| --- | --- | --- |
| SIPA 警告 | 29 条 `ep:1 evt=0x10000` | `sipa_priv.h` 中为 `SIPA_HAL_ERRORCODE_IN_TX_FIFO`；真正 overflow 位是 `0x20000`，full 位是 `0x40000`。通知函数将这三种事件统一写成 overflow。 |
| 发送完成错误 | 同窗口 29 条 `err=2 retry_cnt=10`，29 个不同 DMA 地址 | 位于发送完成描述符回收路径；不是同一个地址反复重试。错误码 2 的硬件定义尚无可靠证据。 |
| SIPA 持续时间 | uptime 2868.570813–2910.638706，平均间隔约 1.502 秒 | 存在持续、周期性完成错误；不能仅凭周期推定报文类型或用户重连定时器。 |
| WLAN 反压 | 通道 10 的累计 rejected submissions 从 2881 增至 2997 | 两个可见采样点之间新增 116 次未接受提交；不是确认丢失 116 个业务包。每次提交可包含多个报文，同一提交也可能重试。 |
| WLAN 提交失败 | 可见 69 条 `push link fail: -11`，另有日志限速提示 | `-11` 为 `-EAGAIN`，当前代码将其作为可重试反压，保留业务队列，不计入原先连续硬失败清队列的预算。日志与此返回码约定相符，但无法单凭文本证明全部配套模块正确。 |
| SIPA 资源变化 | uptime 2864.842785，`WWAN_DL state changed 0->2` | `sipa_rm_res.h` 中是 RELEASED→GRANTED，表示资源授予。不是这里观察到资源被撤回。 |
| 其他控制器异常 | 19 次 `mmc1: Got command interrupt ... no command operation ...` | 是无在途命令时的命令完成中断警告。寄存器转储中的 `Timeout: 0x00000000` 是字段值，不是一次超时的证明。没有足够主机映射信息将其归因于 eMMC，更不能认为 Wi-Fi PCIe 就是这条 MMC 链路。 |

`ep:1` 是 `SIPA_EP_AP`，不是 SIM1，也不能由它判断是哪张 SIM 出错。

`retry_cnt` 是完成回收函数检查描述符地址、匹配发送列表时使用的局部重试预算。
这里地址非零且为 10，不表示基带或业务报文重发了十次。

日志仍有 WCN loopcheck、通道 0 回调及 beacon 更新，没有可见的 assert、Oops、
panic、网络接口重建或基带重启记录；这也不能证明业务网络正常。

## 不应据此下的结论

- 不能把 `sipa overflow` 直接解释为大流量塞满 SIPA FIFO，更不能据此扩大队列。
- 不能用 `edma-tp` 的小数值证明用户没有大流量：通道 10 传输报文地址列表，
  `edma_tp_count()` 累加的是总线 mbuf 长度，不等于全部 Wi-Fi 空口业务字节。
- Wi-Fi 队列反压在此摘录中先于 SIPA 错误，但日志从故障中间开始，不能认定
  Wi-Fi 故障导致 SIPA 错误，或反过来认定 SIPA 阻塞了 Wi-Fi。
- 未出现 `tx return err`/队列清理证据，不能把以前已修的通用 `-1` 触发清队列
  当成本次已经复现的根因。`-EAGAIN` 说明至少对应的总线暂满分类已经存在。
- 错误最后一次出现后还有约 20 秒日志，缺少业务统计，不能宣称已恢复。

## 原厂对照与尚未解决的部分

既有 [F50 原厂模块对照](SIPA-STOCK-COMPARE-20261015.zh-CN.md) 已确认
F50 B09 的 `sipa_sender_notify_cb` 同样把三个事件统一输出为 overflow，
发送回收也没有把 err=2 报文重新提交的分支。这说明日志命名沿袭厂商实现，
不是错误码 2 的定义，也不是 V50 本机原厂模块的验证结果。

当前发送回收路径按 DMA 地址释放 skb，即使描述符带非零错误码也会回收。
不能在不知道硬件错误语义、是否已经部分投递的情况下直接重发。

下一步有效的静态调查是寻找 V50 对应固件/原厂驱动中的描述符错误码定义，
以及核查 PCIe 通道 10 的提交、完成和 pending queue 推进条件。
本摘录没有包头、netid、目标端点、FIFO 深度或完成计数，无法将 err=2
精确归因为校验和、路由、基带流控或某一报文类型。

本轮不以禁休眠、射频重置、扩大队列或强行重发掩盖现象；没有声称完成硬件修复。
