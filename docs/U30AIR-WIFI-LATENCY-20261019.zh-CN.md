后续已通过用户手机的 ADB/root 完成直接 ping、双端逐包对时和手机 TX
completion / 热点 RX MSI 关联，见 [手机直测记录](U30AIR-WIFI-ADB-20261019.zh-CN.md)。
新增证据定位到上行 RX 通知链路；不能将前序反向 ping 的方向推测或短时

## 实测结果

电脑保持 USB 管理连接，不接热点。用户在手机持续 ping 网关；设备另做
有界的反向 ping。反向 ping 可能受手机 ICMP 调度影响，不能等同于手机侧
原始测试的 RTT。以下均为短时样本，不能代表全天的延迟分布。

| 对照 | 反向 ping 样本 | 最小 / 平均 / 最大 RTT |
| --- | --- | --- |
| 第一部手机，原配置 | 35/35 回复 | 4.193 / 60.373 / 212.304 ms |
| 第一部手机，50 ms 间隔诊断小包 | 120/120 回复 | 2.979 / 25.052 / 151.210 ms |
| 第一部手机，恢复 1 秒间隔 | 13/15 回复 | 3.964 / 61.023 / 215.443 ms |
| 第一部手机，hostapd 配置临时 advertisement 0，未验证空口关闭 | 30/30 回复 | 3.052 / 45.737 / 116.294 ms |
| 第一部手机，恢复原配置 | 30/30 回复 | 2.954 / 61.680 / 217.663 ms |
| 第二部手机，原配置 | 35/35 回复 | 5.271 / 66.705 / 198.711 ms |

未回复的反向 ping 不能单独证明空口丢包或热点故障。
短时密集小包仅用于比较，没有保留常驻保活流量。

设备在 wlan0 上被动记录 ICMP 头部标识和内核时间戳，配对手机请求与网关
发出的回复，不记录业务正文。这里测量的是进入主机网络栈到交出回复的时间，
**不包含回复在无线驱动后续队列、固件、空口和手机中的等待**。

| 手机 | 收到的请求 / 配对回复 | 平均 / P95 / 最大处理时间 |
| --- | --- | --- |
| 第一部 | 43 / 43 | 0.341 / 0.446 / 0.562 ms |
| 第二部，90 秒被动窗口 | 89 / 89 | 0.203 / 0.234 / 0.426 ms |

第二部手机测试期间，`push_failures` 保持 19，没有增长。首轮开启已有
RX/BA 诊断时，78 个 ICMP 接收样本均落在 5 ms 内，BA reorder timeout 为 0；
采样完成后诊断开关均恢复为 N。

## 已确认与未确认

### 已确认

1. 两部手机均能复现接近 200 ms 的反向 RTT，不能归为某一部手机独有的问题。
2. 已收到的手机请求在主机内部被很快回复，当前证据不支持把百毫秒尖峰归因于
   IP 应答处理慢或已测到的 RX reorder 超时。
3. 密集小包时平均延迟降低，支持省电缓存或批量收发等待这一方向；不能据此
   区分 AP 固件缓存、空口竞争和手机省电/调度。
4. 测试中曾出现通道 10 的 `-EAGAIN` 暂满；19 是失败提交次数，包含重试，
   不是 19 个丢包。第二部手机的 90 秒窗口没有新增。
5. 一组 `iface_start_xmit ... TX Err` 出现在热点重开、手机 peer LUT 建立之前。
   源码在找不到已关联单播 peer 时会返回 `-EPERM`，可产生相同日志；没有逐包
   返回码和包头，不能将这些日志全部认定为该分支，也不能据此认定手机被踢。
6. 实机磁盘上的 WLAN 模块 SHA-256 为
   `0ad94588f8f998c883170fdac42a6450889277b87d3dae130fd294ffff9155c3`，
   尚未部署公共的 [RX 补充恢复修复](WIFI-RX-REFILL-RESUME-20261019.zh-CN.md)。
   该修复解决总线恢复后继续等待退避的缺陷，但本轮没有证明它是空闲 ping
   尖峰的根因。本轮没有热替换模块。

### 原厂静态对照与限制

原厂 hostapd 的配置生成模板不写 `uapsd_advertisement_enabled`，其 BSS 零初始化
和默认值分支保留该字段为 0；beacon 默认 100 TU、DTIM 默认 2。
OpenWrt 的配置生成器默认 advertisement 为 1。该差异值得核验，但原厂程序的
静态默认值不能代替实际 Android 运行配置，也不能证明没有其他运行时覆盖。

临时修改 hostapd U-APSD 配置的一轮数据有所改善，但仍有 116 ms 尖峰，
且样本量小、重连本身也会改变连接状态。后续核查发现固件实际广播仍开启
U-APSD，所以上述对照不能当作真正关闭 U-APSD 的效果，亦不能用于排除它。

原厂和现有 WLAN 的 power-save 命令均使用两字节的 subtype/value 格式；
原厂 set_power_mgmt 同样发送 subtype 4。本轮仍有 `CMD_POWER_SAVE ARG_ERROR`
和 `CMD_DOWNLOAD_INI` 非零应答，但日志未提供足以定位对应参数的证据，
不能据此直接删除省电命令或替换 RF 配置。

AP 模式 `get_station` 没有可靠的逐客户端速率/信号数据；hostapd 输出中的
`wmm=false`、`ht=false`、`vht=false` 和零速率不能当作真实空口协商结果。

## 首轮结束时的状态与定位边界

临时 UCI 修改已 revert，确认实际 hostapd 恢复 U-APSD advertisement 1、DTIM 2、
beacon 100；没有提交无线配置，没有保留抓取进程或临时设备端程序。

接下来需要将主机 TX 排队时间和固件/空口发送时刻区分开，或取得真实空口的
PM、TIM、PS-Poll/U-APSD trigger 证据。现有网络栈时间戳无法完成这一划分。
在此之前，不通过缩短 DTIM、常驻 ping、关闭全部休眠或取消 WMM 来掩盖延迟。

本地原始记录在 `work/u30air-wifi-latency-20261019/`，未将原厂二进制或用户
无线配置加入 Git。

## 后续：逐包 TX / DMA / RX 工作队列核查

随后继续用第二部手机测量，使用独立 tracefs instance 和临时 kprobe，
按 `sprd_msg`、DMA 地址和 ICMP 标识配对同一个包。结构偏移来自与实机
Build ID / BTF 一致的内核及配套模块调试信息；没有加载新模块。
没有更改系统全局 tracer 或覆盖其他探针。各轮约 35 秒，结束自动删除
instance、探针和临时工具；trace 没有 overrun / dropped events。

### 主机 TX 没有对应的百毫秒积压

U-APSD 仍开启时的 28 个反向 ping：

- 进入 WLAN 发送函数到提交 PCIe：平均 0.211 ms，最慢 0.455 ms。
- 提交到 DMA pop：平均 0.143 ms，最慢 0.235 ms。
- DMA pop 到驱动处理固件 TX 缓冲返回：平均 54.174 ms，最慢 141.039 ms。
- 同轮用户态 ping：平均 56.013 ms、最慢 141.968 ms，28/28 回复。

按 ICMP 标识匹配的 28 个内核 RTT 与“驱动入口至缓冲返回处理”相关系数
约 0.9993；二者差值平均约 1.12 ms。探针窗口没有 host-wakeup-fw 调用，
通道 10 的 192 次提交均成功。这不能扩大为所有负载下均无总线压力。

**这里的 TX 缓冲返回不是已证实的空口 ACK 时间戳。** 它可能包含固件发送、
终端省电等待、固件通知及 RX 通知传递，不能仅凭函数名宣称已经解析了射频时序。

### 密集小包对照可重复，停止后延迟立即升高

保持信道、WMM、DTIM 和 CPU 策略不变，在同一次连接中依次测量：

| 发送间隔 | 样本 | 用户态 RTT 最小 / 平均 / 最大 |
| --- | --- | --- |
| 1 秒 | 10/10 回复 | 6.375 / 71.334 / 194.035 ms |
| 10 ms，仅持续约 5 秒 | 500/500 回复 | 3.070 / 5.649 / 15.317 ms |
| 恢复 1 秒 | 10/10 回复 | 7.048 / 69.199 / 160.624 ms |

密集阶段 500 个包的“发送入口至 TX 缓冲返回处理”平均 4.500 ms，
最慢 5.347 ms。没有把这个诊断流量改成保活服务。
这进一步支持空闲相关的省电/批量收发等待，削弱“CPU 处理不过来／持续吞吐
拥塞导致高 ping”的解释；不能单独证明等待全部来自手机，亦不能完全排除空口重传。

### hostapd 配置关闭后仍复现，继续区分 RX 通知排队

之后按用户明确要求，仅对实机 U30 Air 用公共迁移脚本持久写入 AP `uapsd=0`，
重开热点，核实第二部手机重新接入。备份在设备
`/root/update-backups/u30air-uapsd-20261019/wireless`。
实际 hostapd 配置为 advertisement 0、WMM 1、DTIM 2、beacon 100。
没有部署新的 wifi-scripts APK 或替换生成脚本。

该状态下 28/28 反向 ping 回复，平均 **70.812 ms**、最慢 **193.788 ms**。
第一轮短样本改善不足以认定根因；由于下文确认固件实际广播仍开启，
这轮结果也不足以排除 U-APSD 或其与固件省电调度的交互。

进一步在 PCIe RX 回调、`sc2355_tx_free_data_num` 和实际释放函数间加测：

- 可完整匹配的反向样本中，发送入口到 DMA pop 平均 0.414 ms，最慢 0.520 ms。
- 28 个 TX 返回通知从 RX 解析到公共工作队列处理，平均 0.065 ms，
  最慢 0.169 ms，没有在公共工作队列等 100–200 ms。
- 可按单个 RX mbuf 匹配的 16 个通知，从 RX 回调到解析平均 0.251 ms，
  最慢 0.575 ms。其余批量 RX 回调没有完整逐 mbuf 关联，不能伪称全部已测。
- 空闲高延迟仍对应 DMA 之后、TX 返回通知到达/处理之前的等待。

### 其他核查及结论限制

运行时只有 wlan0 一个 AP、信道 36 / VHT80；没有并发 station 接口。
全局 wpa_supplicant 进程存在并不表示有 station 或正在扫描；没有本轮后台
扫描/离信道事件的证据。`marlin_scan_finish` 是 WCN PCIe 枚举日志，
不能当作 Wi-Fi 扫描。survey 接口未提供可用信道占用数据，不能凭空报告干扰率。

原厂 HAL 虽包含 `wifi_set_latency_mode`，但会先检查 feature bit 30，再通过
vendor 命令发送配置。仅有这个函数符号不能证明当前驱动/固件支持该功能，
本轮没有盲发“低延迟模式”命令。

可以确认主机 TX 排队和已测 RX 工作队列不是百毫秒等待的主要位置。
目前证据主要指向**空闲时固件/空口/终端之间的省电与
收发调度等待**；仍缺实际 Android 同条件运行对照，或空口 PM/TIM/PS-Poll
时间戳，不能进一步硬判为原厂固件缺陷、特定手机缺陷或某条省电命令错误。

未加入常驻流量、未调整 DTIM/CPU、未关闭全部休眠、未修改 AT/蜂窝。
原始跟踪和逐包统计继续保存在上述本地忽略目录。

## 后续发现：配置关闭不等于固件广播关闭

### 已确认的主机与广播差异

在匹配运行内核 Build ID、BTF 的只读诊断模块中，临时探测
`sc2355_start_ap` 的实际输入，捕获的公开 WMM 元素为：

- cfg80211 beacon interval 100、DTIM 2；传入模板 beacon interval 100。
- 单个 WMM Parameter IE，QoS Info **0x01**，U-APSD 位为 **0**。
- 模板未包含 TIM。不能因此认定实际 Beacon 没有 TIM：固件负责生成 TIM。

探针不修改参数；完成一次重开热点后立即卸载并删除临时模块。

电脑仍连原路由器，用 Windows Native WLAN API 只读取目标热点的 BSS IE，
未连接设备热点。热点重开后新 TSF 为 28,369,254 µs 的记录显示：

```text
WMM Parameter IE payload:
00 50 f2 02 01 01 80 00 03 a4 4f 00 27 a4 4f 00 42 43 80 00 62 32 41 00
```

QoS Info 为 **0x80**，U-APSD 位仍为 **1**，参数计数和 AC 参数也不是
直接照搬 hostapd 模板。重复查询得到相同结果，支持固件另外构造了 WMM
广播信息，或覆盖了模板内容。该 API 的信息可来自 Beacon 或 Probe Response，
不是完整的空口监控抓包；因此不能利用记录中缺少 TIM 推断 Beacon 缺少 TIM。
API 边界见 [Microsoft WLAN_BSS_ENTRY 文档](https://learn.microsoft.com/en-us/windows/win32/api/wlanapi/ns-wlanapi-wlan_bss_entry)。

**更正此前推断：尚未完成真正的空口 U-APSD 关闭对照，不能宣称 U-APSD
已被排除，亦不能宣称关闭配置已解决延迟。** 两仓库的配置关闭策略仍保留，
但其对固件广播的实际效果必须单独验证。

### 已排查的另一条路径：PCIe ASPM

只临时关闭 U30 Air 无线端点的 L0s、L1，完成后恢复原值 1/1。
没有改全局 ASPM 策略或运行时休眠策略：

| 状态 | 回复数 | 平均 / 最大反向 RTT |
| --- | --- | --- |
| 原设置 | 12/12 | 74.452 / 120.883 ms |
| L0s、L1 临时关闭 | 24/24 | 55.282 / 181.541 ms |
| 恢复 | 12/12 | 99.056 / 194.529 ms |

短样本未消除尖峰，不支持永久关闭 PCIe 省电作为修复，亦不能证明 ASPM
在任何场景都没有影响。

### 实际固件和进一步修复方向

本轮从实机只读取得的 `wcnmodem.bin` 大小 986,032 字节，SHA-256：
`56a334987dbd7191355ae35345ae99834692324fded5622444cd4eb6f3ae15c1`。
内部版本为 `MARLIN3_20A_RLS2_W24.42.1`，项目 `sc2355_marlin3`。
这只确定本轮 U30 Air 使用的版本，不代表其他机型也使用相同固件。

修复应让 AP 的 WMM/U-APSD、DTIM 配置通过已确认的固件接口生效，并验证
实际广播及终端协商；仅清除驱动能力位、仅修改 UCI 或通过常驻发包维持唤醒
均不足以完成这个目标。原厂 iwnpi 有 `set_wlan_cap`、`set_softap_wfa` 等入口，
但目前没有证据证明它们可单独控制 AP U-APSD；不能凭命令名字写入未知能力
掩码。进一步需对比同一手机在原厂 Android 下的实际广播、PM/TIM/PS-Poll
或 QoS trigger 时序，区分原厂固有等待和移植路径的行为差异。

E5 系列主要使用 SDIO，不能仅凭用户观察的 62 ms 上限断言它与 PCIe 系列是
同一个缺陷，或直接移植总线参数。当前直接实测结论限于上述 U30 Air。

### IP 优先级和信标间隔的后续对照

在同一次关联中，每秒仅发一个诊断 ICMP，轮换并错开四组 IP TOS，
每组 10 个样本，40/40 回复：

| IP TOS | 平均 / 最大反向 RTT |
| --- | --- |
| 0x00 | 62.036 / 138.322 ms |
| 0x20 | 79.861 / 332.212 ms |
| 0xa0 | 50.899 / 126.531 ms |
| 0xc0 | 52.355 / 130.439 ms |

所有组都有尖峰，`push_failures` 前后均为 26。没有逐包采集这轮实际空口 TID，
因此这里只报告 IP 优先级对照，不把它夸大为四个无线 AC 均已完整验证。
不支持把某组优先级一律强制提高作为修复。

再临时将 hostapd beacon interval 改为 50：只读探针确认 cfg80211 值和交给
`sc2355_start_ap` 的帧头值均为 **50**，WMM U-APSD 位仍为 0；同窗口电脑读到
新 TSF 11,680,223 µs 的 BSS IE 仍报告 **100 TU、U-APSD 1**。由于该 API 可取
Probe Response，尚不能据此判断实际 Beacon 发送间隔也必为 100 TU，亦不能
断言全部 AP 参数均被忽略。但它再次表明实际广播信息不能由配置值代替。

信标间隔测试期间手机未持续响应；临时阶段 24 个诊断请求均无回复，恢复后
也未重新关联，不能拿这轮数据计算 50 对 100 的延迟改善或认定 50 导致故障。
已恢复原 UCI（无待提交改动），等待异步热点启动完成后再次读取配置，确认
beacon 100、DTIM 2、advertisement 0；诊断模块已卸载，临时程序已删除。

### 当前可执行的修复路径与验收条件

1. 在同一台 U30 Air、同一部手机上取得原厂 Android 的实际 WMM、Beacon/
   DTIM 和终端省电交互基线；静态程序默认值不能代替这一步。
2. 若原厂空口确实能关闭 U-APSD，追踪其实际下发的 AP 配置/厂商命令，
   在公共 WLAN 路径补齐该控制；若原厂也固定宣告开启，就不能把当前差异
   直接定性为 OpenWrt 独有缺陷，需要继续比对 PM/TIM/PS-Poll/QoS trigger
   到真实下发的时序。现有固件返回缓冲时间还不能替代这些空口时间戳。
3. 若使用原厂 HAL 的低延迟入口，必须先核实 feature bit 30 与驱动 vendor
   子命令支持，并弄清其 AP 模式作用；不能仅据导出函数名字发送 QCA 命令。
4. 修改后同时验收实际广播/协商、空闲延迟、下载吞吐、多终端连接及功耗；
   按 PCIe/SDIO 和实际固件分组，不能只测 U30 Air 就宣称全机型通过。

本轮未找到已验证可单独关闭 AP U-APSD 的固件控制入口，尚未提交驱动修复。
公共配置策略和事实记录已补充，不能把它们称为已完成的空口延迟修复。
