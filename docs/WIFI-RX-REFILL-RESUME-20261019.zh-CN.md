# PCIe RX 缓冲补充恢复修复（2026-10-19）

## 范围

MU300/F50、V50、U30 Air 的 6.18、7.2 使用同一套
`upstream/modules/sprd_wlan_combo`，本次修改公共源码，不按机型增加独立重试服务。
两套构建入口已经从该目录取源码，无需再加一份重复补丁。
本次未修改 E5 仓库的 SDIO 驱动、AT 时序、蜂窝、固件、INI 或 NV。

V50 现场依据及原厂对照见
[日志分析](V50-WIFI-LOG-20261019.zh-CN.md)。日志证明通道 10 反复暂满；
离线执行证明 RX 补充会在总线恢复后仍等待退避，不能将其扩大为所有无线掉线
均已查明原因。没有故障机 RX 缓冲余量和实际逐包延迟记录。

## 改动

- 在 RX 地址提交前标记等待总线机会；只将 PCIe 的 `-EAGAIN` 作为可由 DMA
  完成事件提前解除的退避原因。分配失败、硬错误及 SDIO 保留原有退避行为。
- 通道 10 的成功 DMA 完成通知，提前调度已有 `refill_retry`，再由它回到原来的
  串行 `sprd_work` 队列补缓冲。IRQ 不分配 RX 缓冲、不直接执行补充。
- 在提交前准备好事件标志，并用同一把 IRQ-safe 锁协调事件与定时器设置，
  覆盖“完成先于提交返回/先于定时器设置”，防止零延迟重试被旧退避覆盖。
- 已记录的同一次唤醒会合并重复完成事件；没有总线进展时仍使用原来的
  20–1000 ms 退避，避免固件异常时空转。没有新增轮询、扩队列或延时服务。
- 停止状态与完成调度通过同一把锁同步。RX 初始化完成后才发布指针；
  完成回调的查找受 RCU 保护，退出时停止生产者、取消任务、撤销发布并等待
  已进入的回调，再释放 RX 上下文，避免新增回调带来退出后使用内存。

## 验证

`tests/test_wifi_rx_refill_resume.py` 提取生产函数，用 ASan/UBSan 执行
43 种状态组合，包括：

- 八种退避状态、TX 等待/未等待，以及完成发生在提交中或定时器设置后。
- 零延迟定时器执行前已排队的补充请求、重复完成合并、恢复后再次暂满。
- 没有完成事件时保留定时器重试，分配失败/硬错误不被错误提前唤醒。
- 错误通道、超时通知、SDIO、退出中、RX/TX 上下文尚未发布或已经撤销。

去掉 RX 完成唤醒连接后，同一用例在“总线恢复后应零延迟推进”断言处失败，
可复现旧时序。另检查初始化、停止、任务排空与 RCU 释放的顺序。
离线桩环境验证状态机及 API 使用顺序，不是实际内核并发压力测试。
