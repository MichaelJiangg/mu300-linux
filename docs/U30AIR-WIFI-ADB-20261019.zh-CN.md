# 手机 ADB 直接测试与 PCIe 接收延迟定位

日期：2026-10-19。承接 [前序核查](U30AIR-WIFI-LATENCY-20261019.zh-CN.md)。
以下新增证据优先于前序仅凭反向 ping 对等待方向的推测。

后续已通过双向 A/B/A 找到原厂 CPU0 idle 策略差异，见
[原厂低延迟策略与 CPU idle 对照](U30AIR-WIFI-IDLE-20261019.zh-CN.md)。
不能再把原厂更低延迟理解为两边 CPU 省电条件相同。

## 测试对象及操作

- 热点：前序同一台 U30 Air、同一内核和 WCN 固件；信道 36、VHT80，
  hostapd advertisement 0、DTIM 2、beacon 100。初期采样未更换 WLAN/WCN
  模块；后续仅部署了下文单列的 WCN RX-push 修正。
- 手机：一加 11 / PHB110、Android 14，内核
  `5.15.123-android13-8-00766-gf04dea8b48fa`；ADB shell 的现有 su 可用。
- 手机实际协商 SAE、VHT80、2 空间流，连接速率可达 866.7 Mbps；
  测试初期 RSSI 约 −33 dBm。不能再根据 AP 不完整的站点信息认定它仅支持
  legacy 模式或 1×1。
- 电脑始终连接 CUDY_TR3000，未连接设备热点。直接通过 ADB 执行手机
  `ping -I wlan0`，不再要求用户手动连接或手动读 ping 结果。
- 临时程序只输出 ICMP 地址、类型、标识、序号与内核时间戳；未记录业务正文。
  手机与热点分别使用 AF_PACKET、SO_TIMESTAMPNS 记录同一包四个边界。

## 手机直接 ping 的结果

第一轮亮屏、USB 连接状态下 28/28 回复：

```text
手机 -> 192.168.77.1
RTT min/avg/max = 19.129 / 73.979 / 203.540 ms
```

这是手机实际测得的网关 RTT，不是设备反向 ping 的替代结果。

短时客户端省电对照：

| 操作 | 回复数 | 平均 / 最大 RTT |
| --- | --- | --- |
| `iw` 临时关闭手机 Wi-Fi power_save | 25/25 | 25.237 / 61.652 ms |
| 恢复手机原来的 power_save on | 25/25 | 49.265 / 150.428 ms |
| Android 强制低延迟模式 | 25/25 | 37.806 / 97.137 ms |
| Android 强制高性能模式 | 25/25 | 17.387 / 29.709 ms |

这些窗口提示客户端状态会影响结果，**不能据此认为客户端省电是唯一根因**。
随后同一次双端采样又观察到 power_save on 时平均 40.419 ms，off 时平均
53.828 ms、最大 130.046 ms；直接开关没有稳定消除等待。两种 Android 强制
模式均已撤销，power_save 恢复原值 on；未修改手机持久的驱动配置、CPU 策略
或 Wi-Fi 省电默认值。

## 四点对时把方向分开

记录手机内核发请求 t1、热点内核收请求 t2、热点交出回复 t3、手机内核收回复
t4。对同一包匹配 ICMP 标识/序号。对所有完整样本，时钟差满足：

```text
max(t3 - t4) <= 热点时钟 - 手机时钟 <= min(t2 - t1)
```

这只使用路径耗时非负的边界，不假定上下行相等，也不直接将两台机器的时钟
当作已同步。后续联合样本的单方向估计误差约 ±1.5–1.8 ms；不足以解释
几十到上百毫秒的等待。尚未独立校准两台时钟的频率漂移，因此只用于短窗口。

一轮 18 个正常 1 秒间隔样本的内核边界统计：

| 路径 | 平均 / 最大 |
| --- | --- |
| 手机发出 -> 热点收到 | 55.874 / 136.110 ms |
| 热点收请求 -> 交出回复 | 0.194 / 0.376 ms |
| 热点交出回复 -> 手机收到 | 2.574 / 4.718 ms |

**本轮手机 ping 的主要等待在上行接收路径。** 不能继续将其统称为 AP 下行
U-APSD 队列等待。前序反向 ping 中观察到的下行等待，不能自动等同于此处的
上行等待。

## 手机实际驱动发送完成与热点中断关联

只读取得手机实际正在使用的 `/vendor_dlkm/lib/modules/qca_cld3_kiwi_v2.ko`：
26,607,592 字节，SHA-256：
`ca60dcab8933183ef3f5308d28e6ec77fcad47e2f72766e7666a1e9ebfbea0c4`。

以该模块实际反汇编核实 `dp_tx_comp_process_tx_status`、
`dp_tx_comp_free_buf` 的描述符 nbuf 位于偏移 8；以手机实际内核 BTF 核实
`sk_buff.data` 偏移 216。没有用另一款手机的结构偏移冒充本机 ABI。
在独立 tracefs instance 加入只读探针，关联：

- 手机 `__dev_queue_xmit` -> `hdd_hard_start_xmit`；
- 相同 skb 的 Qualcomm TX completion/status 处理；
- 热点 RX MSI 入口、PCIe 回调、相同通知缓冲的事件处理及 ICMP 接收入口。

手机内核排队至无线驱动通常不到 0.2 ms；另一轮的最大值为 0.582 ms。
手机 TX completion **不是直接的空口 ACK 时间戳**，但可以确认驱动已经处理
对应发送状态，不能把该处理后仍然存在的几十毫秒全部解释为尚未进入手机
无线驱动。

两轮联合采样中，手机处理 TX completion 后，到热点接收网络栈的额外等待
分别仍达到约 **99.9 ms** 和 **82.6 ms**。这些值包含对时估计误差，不能
报告为微秒级绝对空口时延。

## 热点内核收到中断之后并不慢

最后一轮 51 个逐包匹配样本（18 个正常间隔、30 个密集诊断包及 3 个其他
ICMP 请求；分别保留标识，不混作同一次 ping）：

| 边界 | 平均 / 最大 |
| --- | --- |
| 热点 RX MSI 入口 -> WLAN 接收处理 | 0.511 / 1.174 ms |
| 手机 TX completion -> 热点 RX MSI 入口的估计剩余等待 | 19.665 / 82.062 ms |

初次 RX 头偏移探针未匹配到包；短时只读核验后确认，这台固件的实际
`msdu_offset` 为 62，随后按实测偏移抓到上述 51 个完整样本。未将无匹配的
旧探针结果当作驱动没有收到包。

RX 事件中固件自带的 32 位 timestamp 在此窗口呈毫秒尺度递增。减去窗口内
最小基差后，其到主机 MSI 的相对年龄最大约 **82.409 ms**，与“手机发送完成
后到热点 MSI”的剩余等待相关系数约 **0.9979**。其精确取时位置、时钟是否
在部分低功耗状态暂停仍未逆向确认；这是固件/PCIe 通知滞后的佐证，不能
直接命名为某个已经确认的固件定时器。

当前证据把主要问题缩小到 **Wi-Fi 接收之后、主机 RX MSI 到达之前的通知
链路**，包括固件 RX 上报/批处理与 PCIe 中断递送；不能仅凭这些数据再细分
为固件缺陷、MSI 硬件递送问题或具体电源状态问题。

## 省电对照及后续修复边界

只短时禁止接收中断目标 CPU0 的 cluster-pd 状态，保留其他状态，22 个包
平均/最大 34.260/47.341 ms；恢复后 22 个包为 38.246/53.388 ms。两个短窗口
都没有原始 200 ms 尖峰，不能把差异当作永久禁用深度待机的理由，也不能
声称排除所有电源状态交互。状态已恢复为原 disable=0。

前序 PCIe ASPM 对照使用的是反向 ping，其中终端下行等待会混入结果；
**它不足以排除新定位的上行 RX 通知路径受 ASPM 影响**。后续应在手机直接
ping、双端逐包测量的条件下重新做相同链路对照，而不是沿用旧结论。

正确修复应继续对照本机原厂 Android 的 WCN/PCIe 初始化、RX 上报与中断
配置，确认真实控制入口后修改公共驱动路径；不能通过常驻 ping、强制关闭
客户端省电、关闭 WMM、固定提高 CPU 频率或任意缩短未知固件定时器来掩盖。
尚未找到可确认的单一控制字段，本轮未宣称已经提交延迟修复。

## 后续：MSI 分发对照与确定的 RX-push 缺陷

手机经 USB 重新接通后，改为在手机本地后台执行有次数上限的 ping，避免
ADB 传输中断导致测试被终止。软件配置仍为 beacon 100、DTIM 2、U-APSD 0。
PCIe ASPM 临时关闭 16 秒后恢复，保留原省电策略；这是诊断对照，不是常驻
设置。直接上行窗口的固件 timestamp 相对年龄仍可达到约 158 ms。
PCIe 父中断处理最大约 0.435 ms，父处理入口到 WLAN 子中断最大约 0.127 ms。
因此关闭 ASPM 没有消除本轮等待，也不能把等待归因于父中断中的软件排队。

对照实际原厂 `wcn_bsp.ko` 的 `edma_rx_push_isr`（`.text+0x3f588`），发现
公共 PCIe 驱动存在独立且确定的缺陷：`dscr_ring_empty()` 对有效硬件游标
执行 `if (!IS_ERR_OR_NULL(dscr)) return true`，导致 RX-push 中断跳过已完成
描述符。原厂路径直接读取一次游标，检查 NULL/错误，再处理待收描述符，
最后补充接收队列。

已将 `upstream/modules/wcn_bsp/pcie/edma_engine.c` 对齐此处理顺序，并删除
错误的重复判断。没有增加定时器、轮询或关闭省电。真实 C 函数回归覆盖待收
数据、空队列、环形回绕、NULL/错误游标和无空闲描述符，相关 10 项测试通过。
此修复针对 MU300 公共 PCIe 路径；E5 系列使用的 SDIO 不经过这个函数，不能
为了形式上的同步添加不适用的改动。

复用现有构建缓存，只改变 `pcie/edma_engine.c`，编译内核 `7.2.8 #48`
匹配的 WCN 模块，保留 BTF。模块 SHA-256：
`618b400f8b6394ba84728ca1d5f48583654f5a4531baf416d4ce0263f7c76e77`。
热卸载暴露旧驱动 remove 未释放设备节点，重载失败；回退尝试也因残留节点
无法恢复。随后通过正常重启加载修正模块，USB 管理、热点和手机接入恢复。
没有将热重载失败写成修复验证成功，也未将该卸载问题混作本轮延迟根因。

重启后手机 65 个普通 ping 全部应答，平均 67.276 ms、最大 145.961 ms。
另一轮双端采样的普通 18 包平均约 72.5 ms，仍有约 132.7 ms 尖峰。
**该队列缺陷已修，但主要空闲延迟尚未解决；不能把不同短窗口的数值变化
当作性能改善证明。** 本轮 steady-state RX-push 中断很少，亦不能将其称为
所有长等待的原因。

进一步对手机实际模块反汇编核实 TX completion 的 status、release source、
ACK RSSI、TSF 和发送次数字段，新增只读探针。样本包含 status=0 的成功 ACK，
手机处理完成后热点接收仍有约 109.7 ms 的剩余等待。字段释义参考
[Qualcomm 官方 HAL 定义](https://android.googlesource.com/kernel/msm-modules/qca-wfi-host-cmn/+/refs/tags/android-s-preview-2_r0.5/hal/wifi3.0/hal_tx.h)，
实际结构偏移以本手机模块反汇编为准，不直接套另一平台 ABI。
固件 timestamp 的精确生成位置仍待确认。

## 原厂 Android 实际运行对照

随后两次正常切换到本机原厂 Android A 槽，核实同一 eMMC CID、原厂内核
`5.4.254-android12-9-g9444efdc6885` 和上述 Android fingerprint；测完均已
回到 OpenWrt，并恢复原 Linux 默认启动意图。没有格式化或挂载 Android/
OpenWrt 根分区来切系统，没有写 NV 或启动镜像。

手机自动连接原厂热点，确认同为 5180 MHz、802.11ac、2 空间流，手机省电
仍开启。原厂使用 WPA2，65 个普通 ping 全部应答，最小/平均/最大为
**3.240/20.401/70.748 ms**。将 OpenWrt 临时设为 WPA2 后，30 包为
**14.761/61.237/149.017 ms**。认证协议并不足以解释全部差别；SSID、BSSID、
系统背景活动等仍不同，不能称作所有变量一致的严格功耗或性能基准。

在 Android 上直接运行 `sha256sum` 核实，实际使用的 `/odm/firmware/wcnmodem.bin`
及两份 INI 与 OpenWrt **完全相同**：

| 文件 | SHA-256 |
| --- | --- |
| wcnmodem.bin | `56a334987dbd7191355ae35345ae99834692324fded5622444cd4eb6f3ae15c1` |
| wifi_board_config.ini | `47a4e23d96e7334750fdb52b0f283f8f64949605b8ba9df2d835f00ea1f07a1d` |
| wifi_board_config_ab.ini | `c062fd2cafc17b8878b5be1db3861c83dde16e1b1377e913ba77776173c69470` |

最初通过 `adb exec-out su -c cat` 取得的副本曾呈现不同大小和哈希。查明是
本机 Magisk su 的 PTY 将每个 LF 扩展为 CRLF：二进制恰好多 2716 字节，
对应原文件 2716 个 LF；反向还原后逐字节一致，且已由 Android 本机 SHA-256
独立确认。没有将该受污染副本部署到设备。诊断读取改用 Base64 并核验本机
哈希；不得把这一传输伪差异写成固件来源错误。

原厂启动日志确认先打开 STA，调用 `sprd_cfg80211_set_power_mgmt(...,0)`，
再打开 AP。额外命令和角色顺序只作短时对照，尚无稳定延迟收益，不加入
公共启动流程，避免凭一个日志差别引入额外初始化或改变电源策略。

以下其他对照亦未得到足以作为修复依据的结果：

- 明确下发省电通知前后两个 30 包窗口平均 31.895/65.819 ms；探针确认
  subtype=4、value=1/0 均得到成功返回。最终软件状态为原 off，随后冷启
  Wi-Fi 复位临时固件状态。没有永久补发这些命令。
- 短时创建不同 MAC 的 STA、关闭其省电、启动 AP 后删除 STA，30 包平均
  56.292 ms、最大 169.431 ms。最初同 MAC 的并行接口还导致无法接入；
  该轮无有效延迟结果，已撤销。没有加入“STA 预热”的启动兜底。
- 临时将 BSS load 更新周期设为 0，23 秒探针中确实没有固件命令，而普通
  30 包仍平均 68.942 ms、最大 154.421 ms。此前命令只有每 6 秒一组的
  `CMD_SET_IE`，没有证据表明频繁 AT 或无线状态查询导致这轮等待。
- 临时让 CPU0 只使用 WFI、保留其他 CPU 电源策略，30 包平均 37.537 ms、
  最大 78.033 ms；仍存在显著等待，且其他对照窗口也曾低至相似水平。
  40 秒后由设备端 trap 恢复 state1/state2 原 disable=0，不作为禁用休眠的
  理由。运行时 console loglevel 原为 1，无需再靠压低串口日志来处理。
- 网桥 MAC 临时改为与 AP 相同，明确更新手机网关邻居项后，30 包平均
  47.370 ms、最大 66.678 ms，仍未消除等待。先前未更新静态邻居的轮次
  全丢包，不是有效性能样本。原网桥 MAC 已自动恢复，手机邻居项恢复正常。
- 三轮逐包跟踪中，RX-pop MSI 与接收回调分别为 108/108、131/131、251/251；
  未发现先到的空中断被忽略、等下一次中断才收包这一模式。

上述临时 WPA2、BSS load 周期、MAC、CPU idle 和 PCIe 设置均已恢复；保留
原 `sae-mixed`、beacon 100、DTIM 2、BSS load 60 和已授权的 U-APSD 软件策略。
当前唯一新增的常驻驱动变化是确认存在的 RX-push 游标处理修正。主要延迟
仍待定位；不得把失败或有混杂因素的对照作为永久关闭省电、改变网关地址或
缩减无线功能的依据。

## 恢复与适用范围

所有临时内核探针和 tracefs instance 已清理，临时手机/热点程序已删除；
除单列的 WCN RX-push 修正外，未替换内核、固件或 NV，未变更 AT/蜂窝。
新增的原厂模块和
诊断文件保存在 D 盘忽略目录，不复制到 WSL 或加入发布包。

上述直接实测范围为 U30 Air 与这台一加手机。MU300/F50/V50 共用的 PCIe
路径值得同向审查，但还不能把这一轮叫作所有机型的硬件验证。E5 系列主要
是 SDIO，亦不能直接套用 PCIe 配置或数值。
