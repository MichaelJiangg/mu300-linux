# 电脑更新工具兼容没有 od 的 OpenWrt

## 问题

电脑安装器通过 SSH 更新时，读取 misc 的 32 字节启动控制信息使用了
`dd | od | tr`。精简 OpenWrt 不一定提供独立的 od 命令。
管道末尾 tr 成功又掩盖了中间错误，stderr 与 stdout 合并后被当作十六进制解析，
最终显示 `non-hexadecimal number found in fromhex()`，没有指出缺少工具。
这个失败发生在构建新启动镜像、上传更新载荷及写系统之前。

## 修复

- 通过 SSH 原样传输 dd 读取的二进制，不依赖 od、hexdump、base64。
- stderr 独立读取，检查远端退出码和准确的 32 字节长度。
- 保留后续启动控制标识及 CRC 校验，读取错误或短读时停止。
- 上传不再使用 SFTP 子系统，改为 SSH exec 二进制流，逐文件 SHA256 校验。
- 一并上传经过校验的完整静态 BusyBox，只在私有更新目录补齐缺少的命令，
  解决精简系统没有 stat、blockdev 等工具的问题。
- Python 和 Windows EXE 同步；更新 6.18、7.2 两版安装包。

## 验证

- 桌面安装器 33 项测试通过，新增二进制读取、stderr 隔离、短读、流式上传、断线及远端失败用例。
- 实机 V50（7.2.8）没有独立 od；新读取方法获取完整 32 字节，BCAB 标识及 CRC 正确。
- 先完成只读启动控制检查，以及 RAM 临时目录的二进制／空文件上传校验。
- 随后使用 r4 的 Windows EXE，在用户已确认更新的 V50 上完整执行更新：约 25 秒成功，
  正常重启进入 7.2.8；当前锁频、样式、扫描屏蔽文件与仓库一致，热点恢复。
- 无线、APN 和看板配置保留；网络配置仅桥接选项行顺序归一化，配置值相同。
- 重启后未检出 ext4 I/O 错误或模块 BTF／符号错误；蜂窝 WAN 当时仍为 pending，
  本次不把更新流程成功等同于外网通话／数据业务已经验证。
- E5 的 OpenWrt 更新入口使用另一套上传流程，不包含这条 od 管道。

r4 更新安装器与更新脚本，复用本轮刚构建的 r2 系统镜像和内核。
